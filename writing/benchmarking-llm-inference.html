Benchmark the workload, not the model.

A fast benchmark can still lead to a slow product. The test only becomes useful when it resembles the traffic, prompts and constraints your users will create.

← All field notes

Inference benchmarks are seductive because they turn a complicated system into a number. The danger is that the number is often answering a question nobody asked.

A model server that produces an impressive token count under synthetic load may still disappoint in production. Real traffic has uneven prompt lengths, bursts, cancellations, cacheable prefixes and several definitions of “fast.” Before comparing engines or GPU layouts, define the work the system must actually perform.

Start with the user-visible promise

Throughput matters for cost and capacity. It is rarely the only metric a user feels. An interactive assistant is shaped by time to first token. A batch summarization pipeline cares more about end-to-end completion and stable saturation. An agent can be dominated by repeated prefill and model reload behaviour.

I usually begin with four questions:

  • What are the real input and output length distributions?
  • How many requests arrive concurrently, and how bursty are they?
  • Which latency percentile defines an acceptable experience?
  • What happens when the service is saturated or a replica is cold?
A benchmark is a small model of your production system. If the model is wrong, extra decimal places do not make it useful.

Measure a curve, not a winner

A single concurrency level hides the most valuable information: where the system bends. Run a sweep from light traffic through saturation. Record aggregate output throughput, per-user generation speed, time to first token and errors at every point.

As concurrency rises, total throughput generally improves until the server reaches a ceiling. Meanwhile, each user may wait longer. The best operating point is not necessarily maximum throughput—it is the highest load that still respects your service promise.

Practical baseline: report median and p95 time to first token, inter-token latency, request completion time, output tokens per second, and error rate. Include the exact input/output distribution and concurrency beside every result.

Cold, warm and cached are different systems

Compilation, model loading and prefix caching can change a result by orders of magnitude. Label them explicitly. A platform operator needs to understand cold-start recovery; a steady-state capacity test needs warmed replicas; an agentic workflow may deserve its own cache-aware scenario.

Do not let an accidental cache hit become a performance claim. Conversely, do not disable caching when production contains long, repeated system prompts. Test both, because both are real.

Control the variables that quietly move

Performance changes with model revision, quantization, tensor parallelism, engine version, CUDA stack, attention backend and sampling configuration. Keep a machine-readable record of the environment with every run.

This turns benchmarking from a one-off contest into an engineering feedback loop. It also makes upgrades safer: compare a new engine or release against the same production-shaped suite before traffic moves.

The useful result is a decision

The deliverable should not be a leaderboard. It should say which layout to deploy, the expected capacity, the latency envelope, the fallback, and the signals that indicate it is time to scale or revisit the choice.

That is the difference between measuring a model and engineering an inference service.
